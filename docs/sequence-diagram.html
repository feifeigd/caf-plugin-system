🎭 CAF Plugin System 交互时序图

插件加载 → 服务注册 → 消息调用 → 热重载 完整流程

1 系统启动与插件加载

sequenceDiagram autonumber actor Main as main() participant PM as PluginManager participant SR as ServiceRegistry participant LP as LoggerPlugin participant BP as BusinessPlugin Main->>SR: spawn ServiceRegistry Main->>PM: spawn PluginManager(registry, checkpoint) Main->>PM: load "LoggerPlugin" PM->>LP: load library → create → spawn actor PM->>LP: send(init_atom, PM, "") LP-->>PM: init done PM->>SR: register("logging_service", LP_actor) SR->>SR: spawn proxy for logging_service SR-->>PM: registered PM-->>Main: LoggerPlugin loaded Main->>PM: load "BusinessPlugin" PM->>SR: resolve("logging_service") SR-->>PM: return proxy_actor PM->>BP: load library → create → spawn(actor, [proxy]) PM->>BP: send(init_atom, PM, "") BP->>BP: save plugin_mgr ref BP-->>PM: init done PM->>SR: register("business_service", BP_actor) SR-->>PM: registered PM-->>Main: BusinessPlugin loaded
💡 关键点：BusinessPlugin 的 deps[0] 不是 LoggerPlugin 本尊，而是 ServiceRegistry 创建的 proxy actor。

2 插件间消息调用（通过 Proxy）

sequenceDiagram autonumber participant BP as BusinessPlugin participant Proxy as ServiceProxy participant LP as LoggerPlugin BP->>Proxy: send(log_atom, "INFO", "Business started") Note over Proxy: proxy 持有 current=LP_actor Proxy->>LP: forward(log_atom, "INFO", "Business started") LP-->>Proxy: processed Note over BP,LP: BusinessPlugin 全程不知道 LP_actor 是谁
只知道 "logging_service" 这个服务名
💡 为什么用 proxy？ 如果 BusinessPlugin 直接持有 LoggerPlugin 句柄，LoggerPlugin 崩溃时 BusinessPlugin 会收到死信。Proxy 作为中间层，可以在背后无缝切换实现而不让调用方感知。

3 热重载（不中断业务）

sequenceDiagram autonumber actor Admin as 管理员/触发器 participant PM as PluginManager participant SR as ServiceRegistry participant Proxy as ServiceProxy participant OldLP as LoggerPlugin v1 participant NewLP as LoggerPlugin v2 Admin->>PM: reload("LoggerPlugin", path_v2) PM->>PM: 加载新 DLL、创建插件实例（先不 spawn） PM->>Proxy: request(quiesce_atom) Note over Proxy: 进入 paused：新调用连同 promise 一起缓冲
ack 之前的调用已全部委托给 v1（邮箱 FIFO 保证） Proxy-->>PM: true（已静默） PM->>OldLP: request(save_state_atom) Note over OldLP: 邮箱到达序屏障：响应时
全部在途工作已处理完 OldLP-->>PM: state bytes（快照即终态） PM->>NewLP: spawn v2 + restore(state) + init NewLP-->>PM: init done PM->>SR: hot_reload("logging_service", NewLP)（台账） PM->>Proxy: send(resume_atom, NewLP) Note over Proxy: 切到 v2 并冲刷缓冲
ACL 按原始调用方复查 PM->>OldLP: send_exit(user_shutdown) 立即冻结
（丢弃在途异步响应，快照即终态） PM->>PM: down_msg → destroy 旧实例 Note over OldLP: v1 安全退役（状态冻结在快照时刻） BusinessPlugin->>Proxy: send(log_atom, ...) Proxy->>NewLP: forward to v2
💡 零停机热重载（先排空后快照）：Proxy 先静默并把新调用缓冲起来（调用方无感知、请求不丢失），等 v1 处理完在途工作后快照状态并移交 v2，再恢复流量冲刷缓冲；v1 随后安全退出。BusinessPlugin 整个过程完全无感知。

4 插件请求系统关机

sequenceDiagram autonumber actor User as 用户/CLI participant BP as BusinessPlugin participant PM as PluginManager participant GS as GracefulShutdown participant SR as ServiceRegistry participant CP as CheckpointManager User->>BP: send("shutdown") BP->>PM: send(request_shutdown_atom) PM->>GS: forward(shutdown_atom) GS->>SR: send(shutdown_atom) GS->>GS: remaining = ["BusinessPlugin", "LoggerPlugin"] GS->>PM: resolve("BusinessPlugin") PM-->>GS: return BP_actor GS->>BP: send(drain_atom, GS) BP->>BP: 停止接收新请求，处理完在途请求 BP->>GS: send(drain_done, BP_addr) GS->>BP: send(save_state_atom) BP-->>GS: return checkpoint data GS->>CP: save_state("BusinessPlugin", data) CP-->>GS: saved GS->>BP: send(shutdown_atom) BP->>BP: quit() PM->>BP: monitor 检测到 down_msg PM->>BP: destroy_plugin() Note over GS: 对 LoggerPlugin 重复同样的流程... GS->>SR: send_exit(shutdown) GS->>CP: send_exit(shutdown) GS->>GS: quit() GS-->>Main: 所有 actor 已退出
💡 优雅关机顺序：按 shutdown_order 的逆序逐个关闭（依赖方先停，被依赖方后停），每个插件都有机会保存状态到 CheckpointManager。
