- (direction) User requests automatic change tracking and export of database save requests, explicitly including inserts, updates, deletes, nested objects, arrays, and maps; inventory items are independent database records. User authorized continuing into specification and interface design.
- (capability) CAP-1: Track scalar and deep mutations without manual dirty marking. CAP-2: Derive strict insert/update/delete requests from entity lifecycle. CAP-3: Track independently persisted owned collection members. CAP-4: Export atomic unit-of-work snapshots compatible with the EntityStore boundary. CAP-5: Preserve concurrent local edits and unresolved requests across asynchronous acknowledgements and retries.
- (constraint) Current include/common/entity_store_contract.hpp provides field patches, create_if_missing, version checks, request IDs and save results but lacks strict entity CRUD operations. validate(save_request) requires nonempty changes and fields and a single store/partition. docs/entity-store.md documents five adapters and outcome uncertainty. Extend all adapters and wire serialization together; no cross-partition atomicity is available.
- (assumption) Proposed defaults, not individually user-confirmed: C++20 typed wrappers, actor-confined UnitOfWork, explicit prepare_save, client-assigned immutable IDs, one unresolved batch per UnitOfWork, owned collection erase means physical deletion, embedded values use whole-field replacement, player ID is the partition, no automatic root cascade or cross-player transfer in v1.
- (decision) Design proposal: retain immutable request snapshots and per-field mutation generations; advance confirmed baselines only on correlated committed success; keep later edits dirty. Unknown outcomes freeze new exports until the same request ID and payload are reconciled. Strict inserts conflict on existence, updates and deletes require existence and expected versions. Legacy patch behavior remains available to old callers in the upgraded protocol.
- (question) Confirm typed assignment syntax and declared-owned erase semantics; choose root deletion cascade policy; determine whether cross-player transfers and crash-persistent pending batches are required. These unresolved policies must not be silently implemented.
