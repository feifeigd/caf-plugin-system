# CAF Plugin Development (C++ Actor Framework)

Use when working on **caf-plugin-system** (`G:\git\caf-plugin-system`, WSL `/mnt/g/git/caf-plugin-system`) or any CAF-based actor system: hot-reload, plugin lifecycle, service registry/proxy, or typed_actor migration.

## Project facts (verified 2026-08)

- CAF **1.1** via vcpkg (VS2022 manifest build; toolchain auto-detected in CMakeLists). C++20, CMake presets (`windows-x64` etc.).
- Architecture: `PluginManager` + `ServiceRegistry` + `GracefulShutdown` + `CheckpointManager`; messages/tags defined in `include/common/message_tags.def` (X-macro, explicit type_ids 200–999 kernel, 1000+ plugin-private, meta objects via `app_meta::init()` before any actor_system).
- **引导流程（2026-08-22 重构）**：`bootstrap_plugin_framework` 拆成 `bootstrap_system_components`（**任何进程都执行**：spawn registry/checkpoint_mgr/plugin_mgr/shutdown_mgr + 信号 + shutdown 关联；registry 是系统级组件，**不再判空**）+ `bootstrap_plugins`（可选，entry-plugins 非空才跑：扫描/依赖/拓扑/加载/健康 + ready）。纯节点进程白捡 shutdown_mgr 作 master monitor（进程哨兵兜底成死代码路径）。
- **install_stdin_watchdog 合并（2026-08-22，后重构为单参数）**：framework 与 cluster 双份实现合一，公共版在 `framework_bootstrap.hpp/cpp`。初版签名 `(caf::actor target, bool on_eof_exit=false)`（EOF 通知方式参数化：false=shutdown_atom 优雅，true=send_exit 终止节点 actor）；**统一关机重构后删 on_eof_exit，签名 `install_stdin_watchdog(caf::actor shutdown_mgr)`——EOF 一律发 shutdown_atom 给 shutdown_mgr**。顺带修复 cluster 旧版 POSIX 分支缺空管道保护（total==0 误触发）。
- **stdin 交互判定（2026-08-22，ConPTY 坑）**：VS Code cppvsdbg 的 external/integratedTerminal 都是 ConPTY 伪终端，程序 stdin 底层是命名管道——`fstat/_fstat64` 误报 FIFO，导致 `start_console_thread` 跳过、控制台命令无法输入。修复：Windows 分支改用 `GetConsoleMode(GetStdHandle(STD_INPUT_HANDLE))` 判定交互（ConPTY 支持 console API 会返回 TRUE）；失败才走 FIFO 检查装 watchdog。非交互路径日志用 std::cout（CAF logger 会静默丢失，ops_actor.cpp 41 行注释同款坑）。F5 后看日志判断：`console ready` = 可输入；`console input disabled` = 调试器没接 stdin（需换 cppdbg/externalConsole）。\n- **从 WSL 模拟 stdin EOF 触发 watchdog 关机（2026-08-24 实测，裸跑验证用）**：`cmd.exe /c "echo hello | caf_plugin_app.exe"`（必须**有数据后 EOF**）——watchdog 有防误触发保护（`total==0` 空管道 EOF 直接 return 不触发，2026-08-22 为防 WSL→PowerShell 空 stdin 误关机而加）；`< /dev/null`（WSL interop 管道永不 EOF）和 `< nul`（字符设备非 FIFO，watchdog 都不装）都会挂死在 wait_for_shutdown。
- **standalone 控制台（2026-08-22）**：双击/无参数运行默认配置无 node-kind → 原来根本没有 ops 控制台线程（键盘无人读）。修复：main.cpp 在 `!cfg.node_cfg.is_node()` 分支也 spawn ops + start_console_thread，`spawn_ops_actor` 加 `quit_graceful` 参数（true=quit 发 shutdown_atom 给 shutdown_mgr 走优雅关机链；false=send_exit 节点 actor）；关机编排补 standalone 的 `wait_for_shutdown`（否则 quit 后 main 直接 return，析构不等优雅链）。无参数运行默认加载 caf-application.conf 插件 → list/reload 本机热更双击即可用。
- **quit 卡死三连修（2026-08-22，根因全解）**：① ops actor 常驻 → quit 后 actor_system 析构等它永久挂起 → `handle_console` quit 分支加 `this->quit()`；② 混合模式 quit 只 send_exit(client/master) 不触发 shutdown_mgr，main 等的却是 shutdown_mgr → `bootstrap_node` 加 `quit_graceful` 参数（main 传 `!cfg.entry_plugins.empty()`），master/worker 分支 ops 的 shutdown_target 按模式切换（graceful→local_monitor/monitor 即 shutdown_mgr，否则→out.master/out.client）；③ 纯节点 quit 杀 client 后 shutdown_mgr 等系统组件常驻没人管 → main 纯节点分支 wait_for_node_shutdown 返回后 `anon_send(shutdown_mgr, shutdown_atom)` + wait_for；④ `bootstrap_system_components` 尾部补发 `ready_atom`（否则纯节点 shutdown 走 "Not ready, forcing exit" 强杀路径）。验证后门 `--test-quit`（delayed 2s 发 console quit，任何模式）——**三模式（standalone/纯节点/混合 master）全部自然退出 EXIT 0**，优雅关机回归测试必用。
- **统一关机架构（2026-08-22，用户拍板"关机只能由 shutdown_mgr 处理"）**：shutdown_mgr（GracefulShutdown）是唯一关机入口。`register_cluster_atom(266)` 注册 master/client 句柄（main 在 bootstrap_node 后发，存 `cluster_ctls_` vector）；关机链 = 停插件（drain→save→shutdown）→ stop_cluster（send_exit 每个注册的 master/client）→ 杀组件（plugin_mgr/registry/checkpoint）→ quit。**所有触发**（Ctrl+C=framework console_handler / stdin EOF=watchdog / ops quit / 插件请求 / --test-quit）统一发 `shutdown_atom`；main 只剩 `wait_for_shutdown(sys, fw)` 一行。已删：cluster 的 console_handler/signal_handler/node_ctl_ref/wait_for_node_shutdown（bootstrap_node 不再 spawn ops、无 ops_plugin_mgr 参数）。无插件路径立即完成关机（"No plugins to stop"），不等 30s force_exit 兜底；force_exit/not-ready 分支统一走 `finish_shutdown()` lambda。**OpsActor 组件化**：main 无条件 spawn（任何进程都有）——`spawn_ops_actor(sys, node_name, fw.plugin_mgr, nb.master, fw.shutdown_mgr)` + `registry.put("ops")` + `start_console_thread`；master 进程 nb.master 非空 → reload-node/reload-nodes/nodes（管理下级）启用，worker/region/standalone 只管理自己。ops quit 统一 `anon_send(shutdown_mgr, shutdown_atom)` + `this->quit()`。全量重编（touch 多个文件）MSVC 超 500s——用后台构建 + notify_on_complete。
- **Ctrl+C 不能退的根因（2026-08-22）**：quit 能退而 Ctrl+C 不能退 = **ops actor 没被终止**。quit 命令里 ops 会 `this->quit()`（自杀），但 Ctrl+C 是 console_handler 直接发 shutdown_atom 给 shutdown_mgr（不经 ops）→ shutdown_mgr 关机链完成后 main return，actor_system 析构等常驻的 ops → 永久挂起。修复：**ops spawn 后也注册给 shutdown_mgr**（`self->send(fw.shutdown_mgr, register_cluster_atom_v, ops)`），关机时 stop_cluster 统一杀。排查心法：**"进程不退出 = actor_system 析构在等某个常驻 actor"**——main 里 spawn 的常驻 actor（ops/哨兵/测试 actor）要么注册给 shutdown_mgr 统一杀，要么自己有退出路径，否则 Ctrl+C/信号路径必卡。验证后门 `--test-ctrl-c`（直接 delayed_send shutdown_atom 给 shutdown_mgr，不经 ops，模拟 Ctrl+C 路径，EXIT 0 才算过）。
- **Windows 控制台 Ctrl+C 三坑（2026-08-22）**：① **QuickEdit 劫持**——控制台默认开启快速编辑，鼠标划过/选中文本后 Ctrl+C 变"复制"而不是 CTRL_C_EVENT（表现为 Ctrl+C 无法退出）。启动时必须 `SetConsoleMode` 清 `ENABLE_QUICK_EDIT_MODE`（顺带 `ENABLE_INSERT_MODE`）。② **handler 线程语义**——`CTRL_C_EVENT`/`CTRL_BREAK_EVENT` 的 handler 在**系统新建的独立线程**执行（每按一次建一个），`CTRL_CLOSE`/`LOGOFF`/`SHUTDOWN` 才在主线程。信号线程里打印**禁用 std::cout 链式输出**（多次写入会与主线程交错）——用 `fprintf(stderr, "...\n")` 单次原子调用（用户明确偏好：多线程环境不用 std::cout）。③ `SetConsoleCtrlHandler` 重复注册会让 handler 被调两次（双 shutdown_atom）——只在 bootstrap_system_components 注册一次。
- **Windows 控制台关闭按钮（X）——真正的机制（2026-08-23 对照实验推翻旧结论）**：默认行为 = TerminateProcess（拉电闸，不走任何信号）。注册 handler 处理 **`CTRL_CLOSE_EVENT`**（0x02）后，**handler 立即返回 TRUE → conhost 在 ~0ms 内 TerminateProcess（退出码 0xC000013A）**——之前"约 5 秒窗口期"的推断是误诊（半行 trace 残片如 `down_mgr` 本来就是"写入途中被杀"，即 ms 级强杀）。**只有 handler 阻塞不返回时 conhost 才给约 5 秒宽限**（对照实验：裸控制台程序注册 handler，handler 内 Sleep(8000)，SC_CLOSE 后进程存活 4.6s 才被杀；handler 立即返回则 0ms 被杀）。**正确姿势：handler 里 anon_send(shutdown_atom) 后阻塞等待关机链完成（cv，4s 超时兜底），然后 `ExitProcess(0)` 主动退出**——链走完时 checkpoints 已落盘（CheckpointManager 是 tmp+flush+close+原子 rename，ExitProcess 不丢数据；ExitProcess 不跑 atexit/不刷 stdio 缓冲，但关机链的落盘都在 ExitProcess 前完成）。实现：framework_bootstrap 加 `notify_shutdown_complete()`/`wait_for_shutdown_complete()`（mutex+cv），GracefulShutdown::finish_shutdown 末尾 notify；CTRL_CLOSE/LOGOFF/SHUTDOWN 三个 case 统一"阻塞+ExitProcess(0)"。CTRL_C/BREAK 保持原样（console 还活着，进程可自然退出）。**5s 是硬上限，无法延长**：CTRL_CLOSE 的 ~5s 由 conhost 决定，无注册表/API 可调；LOGOFF/SHUTDOWN 受 `HKCU\Control Panel\Desktop\WaitToKillAppTimeout`（默认 5s）控制可调但有限；**唯一无限等待路径 = GUI 窗口（自己的 WM_CLOSE 消息循环，无 conhost 参与）**。因此"关机要 10 分钟"这类需求：要么改 GUI 窗口，要么工程上做**定期 checkpoint + 增量保存**让关机时只存 delta（毫秒级），5s 窗口永远够用——别指望延长 conhost 宽限。**重复触发保护（同批）**：shutdown_atom 在 `shutting_down` 状态直接忽略（trace `[state] already shutting down, ignore duplicate`）——否则 Ctrl+C 后立刻点 X / watchdog+信号双触发会走 "Not ready, forcing exit" 打断正在保存的插件。**自动化模拟点 X + 退出码验证 + 环境探针的完整方法见 `references/console-close-testing.md`**。
  - **两层坑都要防（2026-08-22 实测，一层比一层深）**：
    1. **handler 层**：信号 handler 顺序铁律——**先 `anon_send(shutdown_atom)` 再 fprintf**。点 X 时控制台正在销毁，fprintf(stderr) 可能写不进/阻塞，打印放前面会卡住 handler 导致关机信号根本没发出（Ctrl+C 时控制台还活着打印正常 → **Ctrl+C 生效而 X 不生效的第一层根因**）。打印只是诊断，绝不能阻塞关机信号。
    2. **关机链层（本轮真正卡点）**：shutdown_atom 已到达 shutdown_mgr（trace 有 `shutdown_atom RECEIVED`）但关机链没走完——**shutdown_mgr 收到信号后第一条 `std::cout` 写销毁中的控制台句柄照样阻塞** → 整条关机链卡死 → 5 秒窗口耗尽被强杀（trace 文件只留半行残片如 `down_mgr`）。**修复模式**：全局 `std::atomic<bool> console_closing()`（framework_bootstrap 声明，CTRL_CLOSE_EVENT handler 里先置 true）+ 关机链所有输出统一走 `shutdown_out(msg)`：**先写文件 `shutdown-trace.log`（永远可靠），`console_closing()` 为 false 才 std::cout**（graceful_shutdown.cpp 已全部替换，7 处）。诊断：`shutdown_atom RECEIVED` 有但 `Graceful shutdown initiated` 无 = 卡在关机链第一条 stdout。
    3. **写销毁中的控制台句柄 = 永久阻塞（实测 shutdown_atom 延迟 8~36 秒）**：spdlog stdout sink / cout / printf 全中招——logging_service actor（调度线程）卡住 → 整个调度器排队 → 关机链迟迟不启动。**`freopen("NUL","w",stdout)` 对 spdlog 无效**：`stdout_color_sink_mt` 构造时捕获 FILE*（freopen 改全局 stdout 符号对已捕获指针无效，spdlog 仍写旧控制台句柄）。**正解 = fd 层面重定向**：`_open("NUL",_O_WRONLY)+_dup2(nul,1)+_dup2(nul,2)`（所有 FILE* 共享底层 fd，spdlog fwrite / cout / printf 全部落 NUL 立即返回；需要 `<io.h><fcntl.h>`）。
    4. **静态库 + 插件 DLL 符号副本坑**：插件链接静态库 caf_plugin_core → 静态变量（g_console_closing / console_closing()）在 DLL 里有一份独立副本（永远 false），exe 设的标志插件感知不到 → **插件侧 console_closing 检查必然失效**，只能靠 fd 重定向这类进程级兜底。同类问题：fw_log 的 g_logger 注入在 exe 侧，插件 DLL 同样感知不到。
    5. **窗口关闭 ≠ 进程退出**：handler 返回 TRUE 后 conhost 立即关窗口，**进程在后台继续跑**（卡住时 task manager 有残留）——排查"点 X 没生效"先查 `Get-Process caf_plugin_app`。**诊断 trace 必须带时间戳**（用户两次纠正，曾把"用户点 X 晚几秒"误判成"关机链卡 36 秒"）：signal/event 落盘行无时间戳就无法区分"用户操作晚"vs"handler 后处理慢"——`trace_signal` 也要 `[HH:MM:SS]` 前缀。
    6. **MSVC ofstream 默认 FILE_SHARE_READ → 并发写同一文件失败/阻塞**（shutdown-trace.log 的 trace_shutdown 与 trace_signal 跨线程/跨文件并发打开追加曾卡死关机链，trace 只到 `shutdown_atom RECEIVED` 无 `Graceful` = shutdown_mgr 写 trace 卡住 → 5 秒窗口耗尽被强杀，数据可能没保存）——**必须持全局 mutex**：`trace_file_mutex()`（framework_bootstrap.cpp 定义、hpp 声明，graceful_shutdown.cpp 与 framework_bootstrap.cpp 的 trace 函数共用同一把锁）。**checkpoints/*.ckpt mtime 是"关机链是否真走完"的最终证据**（trace 文件可能因写失败缺行）。
  - **落盘证据（控制台销毁场景唯一可信判断）**：点 X 窗口"一闪而过"是正常机制（窗口销毁中任何输出都来不及看），是否走了优雅链只能看文件——`shutdown-trace.log`（handler 的 `[signal] CTRL_CLOSE_EVENT...` 行 + GracefulShutdown 记录 `[HH:MM:SS]` 行：Graceful initiated / All plugins saved / STOPPED）+ `checkpoints/*.ckpt` mtime 更新（**数据保存 = 优雅；强杀则两者都无**）。排查矩阵：`[signal]` 行 + 三条关机记录 = 完全生效；只有 `[signal]` 行 = 关机链没走（按上述两层坑排查）；什么都没有 = handler 没被调用（查 SetConsoleCtrlHandler 注册 / 旧 exe）。**第三层定位（2026-08-22 细粒度 trace）**：Graceful 后各步骤都埋 trace——`-> sending registry shutdown` / `-> computing stop order` / `-> remaining plugins: N` / `stop_next: resolving → resolved → draining → saved → checkpointed <name>`——trace 停在哪行 = 卡在哪步（如 `resolving` 后无 `resolved` = plugin_mgr 不响应 resolve；`saved` 后无 `checkpointed` = checkpoint 写盘卡）。验证流程：点 X → trace 应有全链 + 进程无残留；**自动化模拟点 X（SC_CLOSE）+ 退出码捕获 + 环境探针对照实验见 `references/console-close-testing.md`**。
- **CAF_LOG_* 全灭（2026-08-23）**：应用侧 52 处 CAF_LOG_* 是死代码（未定义 CAF_LOG_LEVEL → 宏整体编掉，`strings -a exe | grep -c "消息串"` = 0 验证；1.2MB caf-framework.log 纯是 CAF 库调度 DEBUG 噪音），已全部转成 LOG_* 宏（bootstrap 14 / plugin_loader 10 / cluster 4 / plugin_manager 22 / ops_actor 残留 fw_log）。caf-framework.log 已消失（`caf.logger.file.verbosity=info` 无内容可写）。转换注意：`<<` 流式改字符串拼接、lambda 即时调用结果直接 `+`、`fw_log("INFO", msg)` 两参数形态会被 sed 成裸 `log("INFO", msg)` 撞 cmath（见 references/logging-system.md）。
- **日志体系（2026-08-23 重构，用户拍板：写日志只有一个地方 + 必须宏 + 带行号）**：`logging_service` 从插件升级为**系统组件**（LoggerPlugin 与 `framework_log.{hpp,cpp}` 已删除）。**唯一日志头 = `include/services/logging_service.hpp`**（核心与插件共用，src/core 版已删）：
  - **每模块单例**：`current_logger()` = inline 函数 static 局部变量——exe 与各插件 DLL 各持一份（静态库被多模块链接的符号副本问题反用成特性，spdlog 注册表同款机制）。exe 侧 `spawn_logging_service()`（bootstrap_system_components **最先 spawn**）内部自动 `set_logger()`；插件侧 spawn 时 `set_logger(deps[0]) + set_log_source(PLUGIN_NAME)`（deps[0] = ServiceRegistry 解析的 logging_service proxy）。
  - **宏**：`LOG_INFO/LOG_WARN/LOG_ERROR(msg 或 fmt 变参）` → 模板 helper `log_fmt(__VA_ARGS__)`（0 参原样返回运行时串；1+ 参 `fmt::format(fmt::runtime(首参), 其余...)`——**参数必须在 fmt::runtime 外面**，见 references/logging-system.md 坑 6）+ 自动 `[文件:行号]` 前缀 + try/catch 兜底（运行时串含 `{}` 抛异常 → `<log format error>`）。`LOG_FROM(self, level, msg)` 用 `self->send`（关机链 STOPPED 用：与随后同 sender 的 send_exit 构成 FIFO，日志先落再退服务）；`LOG_*_SELF(self, ...)` 插件变体让日志服务经 `current_sender()` 记录发送方 actor（日志行显示 `source#actor_id`）。
  - **actor 追踪必须用 `who->id()` 不是 `caf::to_string(who)`（2026-08-23 实测）**：`to_string(actor_addr)` 渲染 node 级标识，`#` 后段对同进程所有 actor 恒等于进程 PID（日志全显示 `#15316`）——`actor_addr::id()`（actor_control_block 的 id，进程内自增）才是真实 actor id（shutdown_mgr#11、business#16）。
  - **关机链最后退出**：finish_shutdown 里 `send_exit(logging_service)` 排在插件/registry/checkpoint 之后；exit_msg handler 先 flush sinks 再 quit。
  - **console 单一写者**：CAF logger `console.verbosity=quiet`，console 只允许 spdlog；`console_closing()` 检查在日志 actor 的 log_atom handler 内（控制台销毁时丢弃 console 写，关键证据走 shutdown-trace.log——开关机流程单独日志文件，用户拍板保留）。
  - **核心内置服务**：插件 manifest 依赖可引用核心服务——`resolve_dependencies` 用 `@core` 标记预置 `logging_service`（解析时不要求插件提供、不压栈）；ServiceRegistry `register_atom` 自动镜像 proxy 到 `sys.registry()`；ACL `acl_allow` 可写核心服务名（plugin_manager 解析不到插件名时回退 ServiceRegistry resolve，business manifest 已改 `acl_allow={"logging_service"}`）。**注册必须在 bootstrap 显式发 `register_atom{}`**（scoped_actor 里、registry spawn 之后）——漏掉这步依赖解析能过（@core 预置），但插件加载时 plugin_manager resolve 不到 → 运行时 `Missing dependency: logging_service`、所有插件不加载、关机链走 "no plugins to stop"（本次实测踩过）。详细设计/迁移步骤/全部编译坑见 `references/logging-system.md`。

## Core patterns

### Barrier drain (quiesce + request = mailbox-empty proof)
"quiesce 断流：该来的都来了；request 响应：来了的都处理了"
1. `quiesce_atom` to each service proxy, await ack — ack means every call the proxy processed before the ack has been **synchronously enqueued** to the old actor (delegate is synchronous), and no new calls will be forwarded.
2. `request save_state` to the old actor — FIFO mailbox ordering: the response arrives only after all earlier messages processed. **Response itself is the drain proof** (works even if handler returns empty data).

### Retire = snapshot then IMMEDIATE `send_exit` (freeze)
After the save_state barrier, `send_exit(user_shutdown)` **immediately** — do NOT use `delayed_send(shutdown_atom, 2s)`. The delay window lets in-flight async responses (pending-promise callbacks) arrive and mutate state AFTER the snapshot → snapshot ≠ final state. Immediate exit drops everything after the exit message: callbacks never run, state frozen at snapshot. Consistency: CAF auto-delivers `sec::actor_died` for unsettled promises on termination → callers retry against the new instance. CAF atomicity guarantee: callback execution + response delivery happen in the SAME message handling, so "state mutated" ⇔ "caller got response" — no intermediate state.

### Retired instances: never destroy immediately after send_exit
`send_exit` is async (messages queued before exit still process). Move the `LoadedPlugin` into a `retired_` vector and call `destroy(instance)` only in the `down_msg` handler. `down_msg` = termination signal, NOT "resources released" (actor object destructs via refcount, may lag; mailbox leftovers/promise cleanup run later). DLLs are NEVER `FreeLibrary`'d — actor vtables/lambdas live in the DLL code segment and CAF releases refs asynchronously; early unload → 0xC0000005. Handles pool in `plugin_lib_pool()` until process exit.

### Hot-reload provides contract: add-only
`reload_atom` rejects any manifest whose `provides` drops a service (removed service → old proxy permanently quiesced + registry entry pointing at dead actor). Rule: **hot-reload may only ADD services**. New services get `register_atom` (auto-creates proxy) + re-dispatch `set_service_acl_atom` if `acl_allow` declared; existing services get `hot_reload_atom`. Validate BEFORE quiesce so a reject leaves old services untouched.

## typed_actor migration — CAF 1.1 verified constraints
Full details + proof: `references/typed-actor-migration.md`. Verdict: feasible, ~3.5–5 days, proxy/registry/hot-reload stay untyped (transparent). Hard constraints discovered by compilation:
1. `sys.spawn(factory)` derives the handle type from the factory signature — NOT `spawn<Impl>`.
2. typed ↔ untyped requires explicit `actor_cast` (no implicit conversion).
3. A typed actor **cannot `self->send()` to an untyped actor** (static_assert) → `anon_send`/`request`.
4. Typed request to a typed actor **compile-time rejects out-of-signature messages** → plugin-private protocols (envelope, private atoms) must go through the untyped proxy or `anon_send`; `set_default_handler` catches them and responses route correctly.
5. `caf::sec::unhandled_message` does NOT exist in CAF 1.1 — use `caf::sec::invalid_request`.
Lifecycle messages MUST be in the typed signature (save_state is a request; out-of-signature request = compile error on caller side).

## 公共生命周期 behavior（plugin_lifecycle.hpp）— 样板清零

框架固化 5 个生命周期消息的处理骨架，插件只写业务 handler + 注册回调（`PluginLifecycleHooks`：on_init / on_drain / on_save / on_restore / on_shutdown，全部默认空实现）：

```cpp
caf::message_handler business{ /* 纯业务 handler */ };
return caf::behavior{business.or_else(plugin_lifecycle(self, hooks))};
```

- **KEY API FACT: `or_else` 是 `caf::message_handler` 的成员，`caf::behavior` 没有**。CAF 1.1 里 `class behavior` 不是 message_handler 的子类（独立类），`caf::behavior{...}.or_else(...)` 编译报 C2039。组合必须走 message_handler：业务列表用 `caf::message_handler{...}`（变参构造），`or_else` 结果包进 `caf::behavior{...}`（behavior 有 `behavior(const message_handler&)` 构造）。
- **私有在前**：业务 handler 先匹配（高频消息一次命中）；插件在业务列表里写同名生命周期 handler 即覆盖框架默认（or_else 先试前者）。
- 框架统一：drain 回执（`send(coordinator, drain_atom{}, self->address())`）+ shutdown `self->quit()`——插件忘回执/忘 quit 的坑消失；状态序列化走 on_save/on_restore 回调。
- hooks 在 spawn lambda 内构造，回调可捕获 `self`（on_init 里发私有自测消息没问题）。
- 热更新/屏障语义完全不变（save_state 仍是邮箱到达序屏障）。

## CAF_MAIN 入口宏（CAF 1.1，已验证）

手写 main 的历史原因（CAF 0.x 的 id_block 参数）在 1.1 **已不存在**，可放心换 `CAF_MAIN()`（`caf/caf_main.hpp` → `exec_main.hpp`）：

- 宏体：`main() { caf::core::init_global_meta_objects(); return caf::exec_main<__VA_ARGS__>(caf_main, argc, argv); }`
- **模块参数机制只服务 CAF 自带模块**：参数须是 `actor_system_module` 子类或 ProjectIds 类型（有 `begin` + type_id 序列）；自定义类型传进去走 `caf::init_global_meta_objects<T>()` 模板 → 编译失败（integer_sequence 推导失败）。**别传自定义类型，用 `CAF_MAIN()` 空参**。
- **自定义元对象注册的合法窗口 = `app_config` 构造函数**：exec_main 在 cfg.parse 之前、actor_system 构造之前创建 config——把 `app_meta::init() + preregister_plugin_meta("./plugins")` 放进 app_config 构造即可（元对象注册必须在 actor_system 前，CAF 禁止后置 = UB）。
- 白捡收益：cfg.parse 错误统一处理（stderr + EXIT_FAILURE）+ **helptext 检查**（`--help` 自动打印并 EXIT_SUCCESS；手写版会继续构造 actor_system 跑起来——隐藏 bug）。
- caf_main 签名要求：`caf_main(caf::actor_system&, const Config&)`，Config 必须继承 `actor_system_config`（decayed 类型检查）；支持返回 int。

## 类型注册机制：手写 meta vs CAF_ADD_TYPE_ID（跨 DLL 时序，用户明确纠正过）

- **CAF_ADD_TYPE_ID 的 meta 注册发生在静态初始化**（static init）。类型**静态链接进 exe** → main 前注册 ✓ 合法（distributed-nodes 全静态链接就是这么干的，见 `references/distributed-nodes-porting.md`）。类型在 **DLL 且 DLL 在 actor_system 构造后 LoadLibrary** → 注册晚于 actor_system = **UB**——这正是本项目手写 meta（`app_meta::init` + 插件导出 `register_meta_objects` + `preregister_plugin_meta` 提前扫描）的根本原因，**别把插件类型改成 type id block**。
- type id block 可经 `CAF_MAIN(id_block::xxx, ...)` 在 actor_system 构造前注册：block 是 ProjectIds 类型（有 begin + type_id 序列），exec_main 在构造 system 前调 `init_global_meta_objects<block>()`。仅适用于静态链接类型。
- **ID 空间冲突**：type id block 从 `first_custom_type_id` 起自动递增占号段；手写 meta 的 `message_tags.def` 显式 ID 也占同一区（200+）。两机制共存必须错开号段（node block 与 message_tags.def 二选一先占位）。
- 跨进程/跨 DLL 的插件私有消息走 `plugin_envelope` 信封（公共类型静态注册，sub_proto 承载私有协议）——接收方无需加载调用方插件的 meta。
- **X_REG 的类型表达式在展开处必须全限定**：`message_tags.def` 由 `app_meta` 命名空间展开，自定义命名空间类型写 `(caf_plugin_system::node_kind)`，否则找不到类型。
- **协议类型头文件里的 to_string/from_string/from_integer 必须标 `inline`**：头文件被多个 .cpp include，非 inline 定义 → LNK4006 重复定义（warning，第二个被忽略，ODR 隐患）。

## 集群节点模式（master 扁平 + 任意多子树，已实施）

从 distributed-nodes 移植的**集群机制**已落地（`cluster_types.hpp` / `cluster_membership.hpp` / `cluster_master.*` / `cluster_client.*` + framework_config 节点选项），双进程注册/心跳/lease/down 检测验证通过。方案与实施细节、全部踩坑见 `references/distributed-nodes-porting.md`。要点：

- 节点协议类型进 `message_tags.def`（ID 235-253）沿用手写 meta——用户拍板：**优先现有注册机制（插件要动态热更新），只参考集群机制**，不用 type id block。
- 纯节点进程允许空 entry-plugins（bootstrap 用 `if (!cfg.entry_plugins.empty())` 包裹插件引导段）。
- **middleman 模块两步加载**（在 framework_config 构造里，actor_system 前）：`caf::io::middleman::init_global_meta_objects(); load<caf::io::middleman>();`——只 load 不 init → FATAL "I/O module loaded without calling caf::io::middleman::init_global_meta_objects() before"。
- `sys.registry().put(name, actor)` 需要 `#include <caf/actor_registry.hpp>`（actor_registry 是 pimpl，caf/all.hpp 不含完整定义）。
- 部署目录要拷 `caf_io.dll`（vcpkg debug/bin/），否则 exe 秒退零输出。

### 跨节点调用（RemoteCaller）— master 侧服务路由查询 + event-based per-key 队列

完整设计与实施、验证记录见 `references/remote-call-design.md`。要点：

- **别让客户端拉全量拓扑过滤**（旧版 `node_topology_atom` 每次 O(N) 传输+遍历，上千节点不可扩展）：master 新增 `service_resolve_atom(svc)` → `service_route{vector<actor_route>}`，**只返回导出该服务的节点路由**（O(k)，k 通常 1~3）。master 是注册中心，过滤必须在 master 侧做。
- 新协议类型：`X_TAG(service_resolve_atom, 257)` + `X_REG(service_route, 258)` + `X_TAG(cross_call_ex_atom, 259)` + `X_TAG(remote_retry_tick_atom, 260)`（257-260 续在 256 后）。
- **同一 atom 可按 arity 写多个 handler**（CAF behavior 天然支持）：`(cross_call_atom, svc, env)` 与 `(cross_call_atom, svc, node_name, env)` 是两个不同 type_list 签名，receive 里共存无冲突。任意节点 vs 指定节点（复用已有 `node_resolve_atom`）两种调用形态。
- **RemoteCaller 必须是 event-based actor + per-key 队列，不是 blocking_actor**（2026-08 用户拍板重构）：blocking 单线程全局串行——一个 key 的长重试（cross_call_ex 最多 attempts×1s）会堵住**整个** RemoteCaller 线程，其他节点/服务的调用全部排队 = 单点故障放大为集群级故障（用户原话"一个节点可能堵死整个集群"）。event-based 把串行缩小到同 key（in_flight + deque 队列，响应回调才放行下一个）：同 key 严格串行有序，跨 key 完全并行。状态机：enqueue → start → pump → (routes 空 ? resolve : try_route) → connect(异步)/call(异步) → 全失败 retry_or_fail（`delayed_send(1s, remote_retry_tick_atom, key)` 轮间定时，等待期间照常处理其他 key）。详见 references/remote-call-design.md。
- **候选缓存 + failover**：缓存条目持候选路由列表 + round-robin 游标 + healthy 标记；调用失败 → 标记 unhealthy → 游标前进试下一个；**全部候选失败才清缓存**重新 resolve（节点重启/服务热更新后自动恢复）。
- **跨节点调用被 worker 端 ACL 拦截**：business_service 的 manifest 声明 `acl_allow={"LoggerPlugin"}`，master 的 RemoteCaller 调用会被 worker 代理 ACL 拦（worker 日志 `ACL blocked a call to the service`，master 端表现为 `all candidates failed`）——worker 配置必须加 `allow-cross-node = true` 信任远端集群节点。
- **幂等语义已拍板（方案 C）**：`cross_call` 单次立即报错（调用方自定重试）；`cross_call_ex(svc, node?, attempts, env)` 有界自动重试（1s 间隔，attempts 次内成功返回，全败返回最后错误）。幂等性由调用方选入口——信封是字节流无法判断业务幂等。**有序性约束**：同 key 串行 FIFO（RemoteCaller 保证）+ 同 receiver（调用方用指定节点模式保证）；任意节点模式 round-robin 分散多副本，节点间无顺序保证，严格有序必须指定节点。
- 重启窗口期验证法（先启 master 延迟启 worker → attempts 失败 → 上线后自动 OK）见 references/remote-call-design.md。

- **drvfs 时间戳秒级粒度 → MSVC 增量构建漏编译**（2026-08 实测）：WSL 里 patch/write_file 改源码后立即构建，CMake/MSVC 可能判定"文件未变化"跳过重编——若上次编译该文件失败，链接还会用旧 .obj，产物是**旧代码**，构建却 EXIT 0。特征：改的代码没生效、strings 查不到新字符串。修复：`touch` 改过的源文件（mtime 更新到当前）再构建；验证：`strings -a exe | grep -c "<新标记>"`。
- **run/ 目录是手工组装拷贝，构建后不自动同步**（2026-08-22 实测，2026-08-24 用户又踩一次）：MSVC 产物在 `out/build/windows-x64/src/app/Debug/caf_plugin_app.exe`，`run/caf_plugin_app.exe` 是手动拷贝——构建 EXIT 0 ≠ run/ 有新代码（VS Code F5 的 cwd 是 run/，跑的是旧 exe = 调试假 bug 的经典来源）。**exe 和插件/测试 DLL 都要同步**：`run/updates/business_plugin_v2.dll` 曾留旧拷贝（md5 与 `plugins/business_v2/Debug/` 新构建不同），热更加载旧 DLL 疑似导致 worker 崩溃。同步后必须 `strings -a run/caf_plugin_app.exe | grep -c "<新标记>"` 验证；拷贝被锁时先 `Stop-Process`（残留进程锁 exe）。**根治方案（已提议未实施）**：CMake `add_custom_command(TARGET caf_plugin_app POST_BUILD COMMAND cmake -E copy $<TARGET_FILE> run/)`——构建完自动拷，命令行和 F5 都覆盖，一劳永逸。
- CAF_LOG_* 业务日志可能静默丢失（组件未配置），framework log 只见 caf.core/caf.system 行——调试用 `std::cout << ... << std::endl`（必须 endl，强杀进程会丢缓冲）。

## 强引用环 = 常量泄露（2026-08-24 破案：对照实验测不出的那类）

**症状**：dump 恒定 ~200 块/19.8KB，"字节与活动量零相关"曾判为常驻非泄露——但实际有真泄露：**actor 之间互相持有 `caf::actor`（strong_actor_ptr）成员 = 强引用环**。CAF 里 actor 终止 ≠ control block 释放：control block 的强引用数不到 0，actor 对象（含其所有成员引用）就永驻堆上。环是启动期一次性形成 → **常量大小 → 与活动量零相关 → 对照实验/checkpoint diff 必然测不出**。

**本案环图（caf-plugin-system）**：
- `GracefulShutdown::plugin_mgr_`（构造参数持有）→ plugin_mgr；plugin_mgr 经 `request_shutdown_atom` handler 的 registry 查找把 shutdown_mgr 存进成员 `shutdown_mgr_` → 环
- 同类环：ops（`ops_actor.cpp` 成员 shutdown_mgr_）↔ shutdown_mgr（`cluster_ctls_` 持有 ops，register_cluster_atom 注册）；master（membership_registry 的 monitor_actor）↔ shutdown_mgr（cluster_ctls_）
- 静态全局 `shutdown_manager_ref()`（framework_bootstrap.cpp 函数局部 static）永不清除（wait_for_shutdown 里清空行被注释）→ 单方面保活 shutdown_mgr 的 control block

**检测**：grep 所有 actor 类的 `caf::actor`/`strong_actor_ptr` 成员，按"spawn 时把谁传给了谁"画引用图找环。**隔离验证（实锤法）**：注释掉嫌疑 actor 的 spawn 块 → dump 暴跌即证（实测注释 ops/节点块 + 修 plugin_mgr 回指后 205 块/19833B → **1 块/8B**）。

**修复模式（按成本排序）**：
1. **瞬时查找、发送即弃**：只需"给某 actor 发消息"不必长期持有 → `registry().get()` 局部变量，发完即弃，不存成员（plugin_mgr 的 request_shutdown_atom 已改）
2. **删死代码 handler**：注册类 handler 的发送方被注释 = 死代码，整块删（plugin_manager.cpp 的 `(shutdown_atom, caf::actor mgr)` handler，bootstrap:350 发送早注释）
3. **关机时清成员**：finish_shutdown 里 quit 前清 `plugin_mgr_/registry_/checkpoint_mgr_/cluster_ctls_` 等——成员强引用随 actor 对象存活，不显式清 = control block 永活
4. **静态全局 actor 引用必须清**：`shutdown_manager_ref()` 类函数局部 static，关机完成后置空
5. 弱引用方向（actor_addr/weak_actor_ptr）结构性防环，改动最大

**判读修正**："字节与活动量零相关"只能排除**随负载增长**的泄露；**常量泄露（环）用引用链审计 + 隔离法验证**，不能靠对照实验排除。完整排查记录见 `references/actor-reference-cycles.md`。

## CAF 1.1 pitfalls
- **服务引用锚定纪律（2026-08-24）**：服务互依赖会形成强引用环（pluginA→proxyS2→pluginB→proxyS1→pluginA，proxy 的 `ProxyState.current` 是强引用），但 registry 条目持有全部 proxy+impl、plugin_mgr 台账持有插件 actor——两个锚都挂在 shutdown_mgr→`shutdown_manager_ref()` 静态上，正常 return 时静态析构从根解开全链 → 不泄露（0 泄露实测覆盖）。**真正会泄露的是无锚点的环**：临时 spawn 的 actor 互相强引用、不注册不进台账 → 没有静态可达的根 → control block 互相保活到死。纪律：所有长生命周期 actor 必须有锚（服务→registry；插件→plugin_mgr 台账）；临时 actor 之间不互存强引用（用 actor_addr 或单向）。**跨进程（mesh 网状调用）视角**：环是进程内概念，跨进程调用天然无环；mesh 的泄露只来自缓存 remote actor 句柄（本地代理 control block）——长期容器只存 actor_route 数据、必须缓存句柄则 monitor+down 清理、重试有终态（详见 references/actor-reference-cycles.md）。\n- **函数局部 static caf::actor 不需要手动清空（2026-08-24）**：正常 return 路径静态析构在 CRT dump 前执行（标准 [basic.start.term]）→ static 持有的强引用自动释放 → 整个引用链从根（shutdown_manager_ref）递归解开。之前设想的"清 shutdown_manager_ref/清成员"只在 ExitProcess(0) 路径有意义（跳过静态析构），但那条路径不触发 dump，清了无观测价值。**唯一需要弱引用的是线程栈上的引用**：detached 线程被进程退出强杀时不 unwind，局部 caf::actor 析构不跑 → 交互模式下 ops 被线程攥着留在 dump 里（start_console_thread 已改 `actor_addr` 捕获 + 发送前 `actor_cast<caf::actor>` 升级）。\n- **down_msg/exit 竞态 → 实例永不销毁（8B vtable 泄露，2026-08-24 终章）**：正常关机时被 monitor 的 actor（插件）quit 发出的 down_msg 与 monitor 自身（plugin_mgr）收到的 exit_msg **来自不同 sender，无顺序保证**——finish_shutdown 的 send_exit 先到 → monitor quit → down_msg 被丢 → down_msg handler 里的清理（destroy(instance)）永不执行 → `create_plugin()` 的 `new BusinessPlugin()`（**纯 vtable 对象 = 恰好 8 字节**）泄露。**修复模式：monitor 加 exit_msg handler 兜底销毁全部实例再 quit**（down_msg 路径已 erase 的不会双删）。**定位判据**：8B 块 + Data 是 0x7FFE... 高地址（DLL 代码段 vtable 指针）= 插件实例对象；无插件对照（`entry-plugins = []`）→ dump 全空 = 插件侧。战果全链：205 块/19.8KB →（环修复）→ 1 块/8B →（exit_msg 兜底）→ **0 块/0B**。
- **`anon_send(actor_addr)` 编译不过（CAF 1.1 实测，别再推荐这个 API）**：send.hpp 的 Handle 模板直接 `receiver->enqueue()`，actor_addr 无 `operator->`（C2819/C2039）。**正确姿势：捕获 addr（弱引用），发送前手动升级** `caf::actor_cast<caf::actor>(addr)`（weak_ptr_upgrade_cast → get_locked，actor 已死返回空则跳过）。actor_addr 内部 = `weak_actor_ptr`（actor_addr.hpp:128，`has_weak_ptr_semantics=true`）——**不保活 control block**；`caf::actor` 直发更快（0 额外开销），addr 每次发送多 1~2 个原子操作（weak→strong 升级）。选型依据是生命周期不是速度：长生命周期 detached 线程/静态存储必须用 addr（或瞬时引用），高频热路径才用强引用。另：anon_send/delayed_anon_send 已标 `[[deprecated("use anon_mail instead")]]`（send.hpp）——将来统一迁 anon_mail。
- **detached 长生命周期线程捕获 `caf::actor` 强引用 = 保活风险（2026-08-24）**：控制台 getline 线程交互模式下**没有自愿退出路径**——唯一自然退出 = stdin EOF（getline 返回 false）；Ctrl+C 关机时线程还阻塞在 getline，被进程退出强杀（栈直接回收，不跑析构）。捕获强引用 → 目标 actor 的 control block 被线程攥到进程死 → dump 报泄露（WSL 管道测试看不到，因为非交互线程根本不启动）。**修复：捕获 `caf::actor_addr` + 发送前升级**。"线程退出了吗"的证据 = while 循环后放 `fprintf(stderr, "[console] thread exiting (stdin EOF)\n")` 标记：EOF 场景可见，交互 Ctrl+C 永远看不到 = 反证是被杀不是退出（多线程打印用 fprintf 单次原子写，不用 std::cout 链式）。
- **Empty behavior kills the actor**: `caf::behavior{}` with only a default handler → actor exits immediately. Real `spawn_service_proxy` survives because its behavior has quiesce/resume/set_acl handlers. Any new actor needs ≥1 real handler.
- **middleman `remote_lookup` 返回 `strong_actor_ptr`（非 expected）**：空检查 `if (!remote)`；转 actor 用 `caf::actor_cast<caf::actor>(std::move(remote))`。`connect(host, port)` 返回 `expected<node_id>` 才有 `.error()`。
- **CLI 选项全名带组前缀**：`--caf-plugin-system.node-kind=master`；省略前缀 → `not_an_option`。--help 输出里就是全名。
- `down_msg` handler must check `retired_` before the live `plugins_` map (retired instances are cleaned there, not treated as crashes).
- unregister-then-quiesce ordering: `unregister_atom` retires the proxy — resolve first, quiesce, then unregister, then send_exit.
- **同一 atom 多 handler 合法**：CAF 按完整消息签名（type_list，含参数类型与 arity）匹配 handler，`(cross_call_atom, string, plugin_envelope)` 与 `(cross_call_atom, string, string, plugin_envelope)` 是不同签名，receive 里共存无冲突（RemoteCaller 双形态调用实测）。只有 arity+参数类型完全相同的 handler 才是重复定义。
- **`caf::result<T>` 没有 `operator bool`**（error C2451）：判别成功/失败用 `caf::expected<T>`（单轮尝试函数返回 expected），handler 出口再包回 `caf::result<T>{std::move(*res)}` 或 `{std::move(res.error())}`。result 只能作 handler 返回值，不能作中间判别对象。
- **blocking_actor = 每实例一个专用 OS 线程**（detached，非调度器线程池）：receive 阻塞不占 worker；退出时线程 join。适合低频控制面 actor，**别当业务 actor 模板**（千级实例 = 千线程）；**更别用它做跨节点调用客户端**——单线程全局串行，一 key 长重试堵全部（RemoteCaller 已重构为 event-based，见集群节）。
- **blocking_actor 等待循环必须可中断**：`receive([&](caf::exit_msg&){ running=false; }, caf::after(1s) >> []{})`——send_exit 只投递消息不打断线程，若等待循环不监听 exit_msg，线程仍在 sleep，actor_system 析构 join 卡死（优雅关机被拖住）。内层 receive 消费 exit_msg 安全：running=false 后外层 while 退出，act() 返回 = 终止。\n- **scoped_actor 析构 ≠ 等 send 的回复**（2026-08-23 确认）：析构 = `cleanup(exit_reason::user_shutdown)`（给自己发退出）+ `join()`（等自己终止；blocking actor 跑在创建线程上，join 基本立即返回）。**send() 是 fire-and-forget**，CAF 不追踪、析构不等；析构时 mailbox 关闭，迟到的回复直接丢弃（不挂起）。真正会"等"的只有：① `request().receive()` 在调用点阻塞等回复（不是析构）；② **actor_system 析构等所有常驻 actor 终止**——控制台线程 scoped_actor 挂死进程的根因就是这条（actor 永不退出），不是"析构等回复"。**scoped_actor 适用场景 = 函数作用域内的同步引导/编排**（bootstrap、main）；**长生命周期线程（控制台 getline、watcher）绝不能用**——用 `anon_send`。bootstrap_system_components 里用 scoped_actor 而非 anon_send 的原因：sender 身份可溯源（将来可加 `current_sender()` 校验）、可升级成 `request().receive()` 同步确认、CAF 日志可归属；当前两个 send 接收方都不看 sender 不回执，anon_send 也能跑，但那是降级。
- **`remote_lookup()` 是阻塞的**（头文件注释明说 "Blocks the caller until nid responded"）：event-based actor 里不能直接调（会卡调度线程）。**用 middleman actor 异步接口**：`request(mm.actor_handle(), timeout, caf::connect_atom_v, host, port)` → `result<node_id, strong_actor_ptr, set<string>>`（connect_atom 是 CAF core 自带 atom，`caf::connect_atom_v`，无需自注册）。lookup 只在首连时同步一次（毫秒级可接受），之后 target 缓存复用。
- **异步回调捕获按 index 不按引用**：`.then` 回调里访问候选列表元素必须捕获索引（`ks.routes[idx]`），不能捕获 `auto& route`——回调执行时 vector 可能已 clear/重填（全 unhealthy 清缓存重 resolve），引用悬垂。回调里修改用 `ks.routes[idx].healthy = false`。
- **`caf::result<T>` 可从 `typed_response_promise<T>` 构造**（`result_base(const response_promise&)`）：异步延迟响应的标准姿势是 handler 里 `auto rp = make_response_promise<T>(); ...; return rp;`，后续 `rp.deliver(value)` / `rp.deliver(error)` 补响应（deliver(expected<T>) 也行）。event-based actor 无需 response_promise 成员持有——rp 随消息流传递。
- **同机多进程 node_id 相同 → 跨进程 sender 失效**（CAF 1.1 实测）：host_id 基于 IP（同机相同），跨进程消息的 sender actor_addr 在接收方会被当作本地 actor 解析 → 查找失败/为空，`current_sender()` 可能返回空。**不能靠 `sender->node() == self->node()` 判断跨节点**（会误拒同机部署）。response promise 回执不受影响——rp.deliver 照常路由回发起方（remote_reload 回执就是这么通的）。

### 运维功能（OpsActor）— master 远程热更 + 每节点本地控制台（2026-08 实施）

需求：master 可热更任一节点；每节点控制台可热更本机指定插件。已实施，构建/双进程验证见下：

- **协议（内核固定，非 envelope）**：message_tags.def 261-265——`remote_reload_atom(261)` + `reload_request(262)`（plugin_name/file_name/dll_bytes/dll_path，双模式）+ `reload_result(263)` + `console_cmd_atom(264)` + `list_plugins_atom(265)`。**运维协议是内核固定功能，跟插件 envelope 两回事**（用户明确过）：走显式 type_id + 结构化类型，`vector<std::byte>` 只是载荷字段。
- **OpsActor**（`src/core/cluster/ops_actor.*`，每节点一个，registry 名 `"ops"` + exported_actors 上报）：本地控制台（help/list/nodes/reload/reload-node/reload-nodes/reload-all/quit）+ 远程热更（master→remote_reload→落盘→转调 PluginManager reload_atom）。批量 = do_remote_reload 提取回调 + BatchState 共享计数，协议零改动。
- **双模式**：dll_bytes 非空 = master 读本地 DLL 推送（节点落盘 `updates/<plugin>/<ts>-<pid>/` 新路径，PID 后缀防同机多 worker 同秒撞路径）；否则 dll_path 已就位路径模式。reload-node 命令按"master 本地存在该文件"自动切换。
- **master 寻址**：`node_resolve(node, "ops")` → actor_route 只是连接信息（host/port/actor_name），要 `middleman connect_atom`（返回 node_id,strong_actor_ptr,set<string>）+ `remote_lookup("ops", nid)`（阻塞，首连一次）→ actor_cast，再 request。RemoteCaller 同款模式（remote_caller.cpp do_connect）。
- **安全（终版，2026-08-22 实测修正）**：**不做 sender 拒绝校验**——CAF 同机多进程 node_id 相同（host_id 同 IP，master+worker 同机实测相等），跨进程消息的 sender 在接收方被解析成本地 actor 查找 → 失效/为空，校验会误拒所有同机部署。安全边界 = middleman 端口可达性 + 集群互信（allow-cross-node）；sender 仅记日志审计。**所有 `sender->` 解引用必须判空**（实测 `sender->node()` 空指针 → worker 进程 0xC0000005 崩溃，master 侧表现为 request_timeout + `remote_link_unreachable`、进程数 2→1）。reload-node 仅 master 进程可用（需 master_registry 句柄）。
- **控制台线程**（start_console_thread，2026-08-22 二次修复）：std::thread + getline → **`caf::anon_send(ops, console_cmd_atom_v, line)`——绝不能用 `scoped_actor`**（线程阻塞在 getline 等键盘输入，其持有的 scoped_actor 本身是 CAF actor 永不退出 → actor_system 析构等它 → 进程挂起。这是 \"Ctrl+C 能退而 quit 不能退\" 回归的根因：quit 走优雅链 → main return → 析构卡在控制台线程的 scoped_actor；`--test-quit` 不触发因为 WSL 管道下控制台线程压根没启动）。anon_send 不需要调用者上下文，任意线程安全；detached 线程随进程 exit 被 OS 终止，无需显式退出。**FIFO stdin（WSL 管道）时跳过**——install_stdin_watchdog 也在读 stdin，两线程抢读同一管道会互吃数据；交互终端（非 FIFO）watchdog 不装，控制台线程正常工作。签名 `start_console_thread(caf::actor ops)`（不再传 sys）。**2026-08-24 更新：捕获改 `caf::actor_addr` + 发送前 `actor_cast<caf::actor>` 升级**——线程交互模式下活到进程退出（被强杀），强引用捕获会保活 ops 的 control block → dump 泄露；循环后加 EOF 退出标记（fprintf 单次原子写）作"线程是否自愿退出"的证据：EOF 路径（Ctrl+Z/关窗口）可见，交互 Ctrl+C 永远看不到 = 反证被杀。**注意 `anon_send(actor_addr)` 编译不过，必须手动升级（见 CAF 1.1 pitfalls）**。
- 接线（2026-08-22 组件化后）：**main.cpp 统一 spawn**（任何进程都有）——`spawn_ops_actor(sys, node_name, fw.plugin_mgr, nb.master, fw.shutdown_mgr)` + `registry.put("ops")` + `start_console_thread`；master 进程 nb.master 非空 → 远程管理命令启用。bootstrap_node 不再 spawn ops（签名只留 sys/settings/local_monitor/out）；节点侧 `cc.exported_actors.push_back("ops")` 上报导出供 master node_resolve。
